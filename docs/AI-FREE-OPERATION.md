# AI-free operation

## Why this document exists

The live deployment of WTY runs on a **local secure network**: no outbound internet, no AI service, no third-party API calls. Stakeholders need explicit, audit-trail-grade evidence that the dashboard's narrative outputs (the headlines, the executive summary, the recommendations) are produced by deterministic rules in our own code - not by an LLM or any other AI service.

This file is that evidence.

## Headline claim

> Every analytical narrative this application produces - the auto-generated headline cards on the dashboard, the long-form `REPORT.md` analysis, the per-page widget explanations, and the recommendations in the Action Dashboard - is generated by **hard-coded deterministic Python/TypeScript rules**. There are zero LLM, ML, or AI-service dependencies anywhere in the codebase.

## Narrative generation - how each one actually works

### 1. Auto-headline cards on the Overview tab

**Endpoint**: `GET /api/analytics/headlines`

**File**: [backend/src/routes/analytics.ts](../backend/src/routes/analytics.ts) - search for `router.get('/headlines'`.

**Logic**: a sequence of hand-coded if/else rules. For example:

```ts
// Card 1 - regime impact (always emitted when pre + post data exist)
const accDelta = ((post.accept/post.n) - (pre.accept/pre.n)) * 100;
const rejDelta = ((post.reject/post.n) - (pre.reject/pre.n)) * 100;
headlines.push({
  kind: accDelta < -5 ? 'warn' : 'info',
  icon: 'shield',
  title: 'Vetting regime impact',
  body: `Accept rate ${accDelta.toFixed(1)} pp ... post-Jan 2025`
});

// Card 2 - Cannot-Detect surge (only if last 3 mo rate > 3x earlier 6 mo)
if (factor > 3) {
  headlines.push({ kind: 'bad', icon: 'eye-off', title: '"Cannot Detect" surge', body: ... });
}

// Card 3 - top failed part (always)
const [topPart] = await Claim.aggregate([...]);
headlines.push({ kind: 'warn', icon: 'wrench', title: 'Top failed part', body: `${topPart._id} ...` });
```

Every headline that ever appears was written by a human as a template string + threshold. There is no model inference; the same input data always produces the same headlines.

### 2. Long-form `REPORT.md`

**File**: [scripts/report.py](../scripts/report.py)

**Logic**: 700+ lines of pandas / numpy / regex. The script:

1. Loads `claims.csv` with `pd.read_csv`.
2. Cleans dates, hours, derives partCode, regime, tags via a regex dictionary.
3. Computes every aggregation directly: claim counts, accept rates, DOA shares, chi-square on regime x outcome via `scipy.stats.chi2_contingency`.
4. Writes the report by stitching together pre-written template strings interpolated with the computed values, e.g.:

```python
parts.append(
  "- **Dataset**: {n:,} claims across {nmodels} machine models, ..."
  .format(n=n, nmodels=df['Machine Model'].nunique(), ...)
)
```

5. Recommendations and the Action Dashboard at the end of `REPORT.md` are **literal strings** in the script - they are not generated; they were written by a human after reading the data. Future versions can expand them, but they are never produced by an LLM.

### 3. Widget descriptions and info tooltips

Every chart card and KPI tile passes `info`, `formula`, and `source` strings as React props. These strings are written in the source code (in each `*Tab.tsx`). The (i) tooltip in the dashboard renders those strings verbatim.

Example from [frontend/src/pages/Dashboard.tsx](../frontend/src/pages/Dashboard.tsx):

```tsx
<KpiTile
  label="True accept rate"
  info="Share of vetted claims whose outcome is exactly 'Accept'. Z-Code is treated as a non-accept per the vetting team's KPI rule."
  formula="count(claimOutcome=='Accept') / count(claimOutcome!=null)"
  source="claimOutcome"
  ...
/>
```

No string generation at runtime; what you see is what was committed.

### 4. Per-claim narratives

There is no per-claim narrative generator today. The Claim modal displays the raw `description` and `vettersNotes` fields verbatim - they are written by the customer / dealer / vetter.

A future enhancement (tracked in [IMPROVEMENTS.md](IMPROVEMENTS.md)) would add a per-claim "Why was this rejected?" template that interpolates values from the claim's own fields (area, theme, supplier, tags) into a hand-written template - still 100 % deterministic.

## Outbound network audit

The backend (`backend/src/index.ts`) makes only the following outbound connections at runtime:

| Connection | Why |
|---|---|
| `mongodb://localhost:27017` | Local Mongo connection for queries |
| `readFile` of local `REPORT.md` | Serves the markdown file to the Full report tab |

There is no `fetch`, `axios`, `https.request`, or any other outbound HTTP call in the source. The browser-side code calls `/api/...` paths only - those are same-origin to the backend on `:4000`.

To re-audit, run:

```bash
rg -n "(fetch|axios|http\.request|https\.request)" backend/src
```

Expected hits: zero in `backend/src/` (frontend `fetch('/api/...')` calls are same-origin to the same process and serve as the routing layer).

## Operational implications for the air-gapped go-live

- **No DNS resolution required** for any AI domain. Block `*.openai.com`, `*.anthropic.com`, `*.googleapis.com`, `*.huggingface.co` etc. at the network layer - WTY won't try to reach them.
- **No outbound proxy needed** for the dashboard to work. The only network requirement is "the browser must reach `:4000` on localhost (or wherever the server runs)" and "the server must reach `:27017` for Mongo".
- **No tokens / API keys** are needed in `.env`. The shipped `.env.example` only has `PORT`, `MONGO_URI`, `MONGO_DB`.
- **No model files / weights** are loaded at startup. The startup log shows only `Mongo connected` and `API listening`.

## What "deterministic" buys you

Because every narrative is rule-driven, identical input data **always** produces identical output text. That gives you:

1. **Reproducible analyses** - re-running the same CSV regenerates the same `REPORT.md`. Auditors can verify.
2. **No hallucination risk** - the system can't invent numbers or attribute false causes. It can only do what the code says.
3. **Easy to extend** - adding a new headline rule, recommendation, or tag is a code change in a clearly named function, reviewed in version control.
4. **Easy to defend** - "where did this number come from?" maps to a single line of Python or TypeScript. Always.

## What you'd add for richer narratives without crossing the AI line

All of these stay rule-based and local-only. They are listed in [IMPROVEMENTS.md](IMPROVEMENTS.md):

- More headline templates with finer thresholds.
- Per-claim "why" templates: select a sentence from a dictionary based on `(area, theme, supplier, tags)` tuple.
- Auto-suggested tags: extract bigrams that occur > 50 times and aren't in the controlled vocab; surface them in Admin -> "add as tag?".
- Survival / Kaplan-Meier curves per model (one-pass deterministic).
- Recurrence flagging: machines with >= 3 claims AND >= 6 months between first and last marked "likely future claim" - one if-statement, no model.
- Auto-recommendations: re-rank parts by `count * (DOA share + reject rate)` and emit the top 5 as bullet points - deterministic recipe.

If anything in this audit looks stale, re-run `scripts\audit-no-ai.bat` and the relevant `rg` greps above. The audit is intentionally simple to run, so it can be repeated on every release.
